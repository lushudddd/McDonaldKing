# 麦门省钱助手（mcd-saver）

## 概述

解决一个真实困境：点一份麦当劳，用户要在抖音、美团、官方小程序之间来回切换手工比价，还要在脑子里算配送费、券门槛、有效期。本 Skill 把这个过程收敛为一句话——**官方渠道（App/小程序）由 AI 通过麦当劳 MCP 精确计算到分，抖音/美团价格由用户报数，总账由 AI 对齐口径后算清，直接给出"去哪个渠道买"的结论**。同时覆盖领券、最优价下单、积分变现，形成完整省钱链路。

## 前置条件

1. mcd-mcp 连接器已启用（Streamable HTTP 接入 `https://mcp.mcd.cn`，请求头携带 Bearer Token）。
2. 涉及"今天 / 本月 / 最新"等时间语义时，先调用 `now-time-info` 确认当前时间，再继续后续流程。
3. MCP 服务限流 600 次/分钟；批量比价（多张券逐一试算）时控制调用节奏，收到 429 时向用户说明并稍后重试。

## 工作流决策树

用户诉求进入后，按以下规则路由（可组合执行）：

```
用户提到 省钱 / 优惠 / 哪个便宜 / 抖音 / 美团
├── 抖音/美团/小程序哪个便宜 / 跨平台比价 ..... → 工作流 E：跨平台比价（招牌能力）
├── 只想领券 / 看有什么券可领 ................ → 工作流 A：每日领券
├── 要点餐且希望最划算 ...................... → 工作流 B：省钱点餐（官方渠道精算引擎）
├── 问积分余额 / 想用积分兑换 ............... → 工作流 C：积分变现
├── 想看资产全貌（券 + 积分） ............... → 工作流 D：资产盘点
└── 问最近有什么活动 / 优惠活动 ............. → campaign-calendar 查询后汇报，
                                                 有可领券活动时主动引导工作流 A
```

路由规则：工作流 E 内部复用 B 的比价引擎（E2 直接执行 B1–B3）；进入 E/B 前先执行工作流 A（领券不亏，为比价备弹药）；任何下单动作必须走完比价步骤。

## 工作流 E：跨平台比价（招牌能力）

用户主诉"抖音/美团/小程序哪个便宜"时进入。设计原则：**AI 负责官方渠道的精确计算，用户负责外部平台的报价录入，比价结论用总账口径。**

### E1. 锁定比价标的

- 确认用户想吃的商品/套餐，并与官方规格对照（如"巨无霸中套餐"= 巨无霸 + 中薯 + 中可乐；必要时用 `query-meal-detail` 确认套餐组成）。
- 确认就餐方式倾向：到店 / 外送 / 都行。这直接决定外部团购券是否可用（多数团购券仅支持到店核销）。

### E2. 官方渠道精算（复用工作流 B 的 B1–B3）

- 到店场景：产出"到店最优到手价"（优惠券矩阵试算后的最低应付价）。
- 外送场景（用户有外送意向时）：产出麦乐送**含配送费**的到手价。
- 积分替代方案：若积分可兑同款/近似商品券，一并纳入比较（衔接工作流 C）。

### E3. 外部平台报价录入

- 询问用户外部报价："抖音/美团上这个套餐多少钱？套餐里有什么？"
- 解析录入四个字段：平台、价格、套餐内容、限制条件（有效期 / 可用时段 / 核销方式）。
- 用户未提供且无法确认的限制项，在对比表中如实标注"以券面规则为准"，不得臆测。

### E4. 口径对齐（比价结论可信的关键）

按 `references/platform-deals.md` 的三重对齐规则执行：

1. **规格对齐**：外部"套餐"与官方套餐逐项对照（主餐是否同款、薯条/饮料尺寸、是否含小食）；规格不同须折算差额或建议加购对齐后再比。
2. **就餐方式对齐**：仅到店核销的团购券在外送需求下直接出局；美团外卖报价须加配送费、包装费后与麦乐送到手价对比。
3. **总价口径**：所有方案统一折算为"到手总价"（商品金额 − 优惠 + 配送费/包装费 + 凑单加购），禁止用券面价与到手价混比。

### E5. 总账对比与推荐

- 输出总账对比表：渠道 / 到手总价 / 规格差异 / 就餐方式 / 限制条件（模板见 `references/platform-deals.md`）。
- 先过滤（不满足就餐方式的方案出局），再按到手总价升序推荐；**价差 < 2 元**时把"便利性"（官方渠道可直接下单、累积积分、可退款、免核销）作为加分项明确提示，给出倾向性建议但把决定权交给用户。
- 用户选官方渠道 → 无缝衔接 B4 下单；选外部平台 → 提示核销方式与有效期注意事项。

## 工作流 A：每日领券（被动省钱）

1. 调用 `available-coupons` 查询麦麦省当前可领的优惠券列表（无参数）。
2. 调用 `auto-bind-coupons` 一键领取全部可领的券（无需指定 couponId）。
3. 调用 `query-my-coupons` 确认卡包到账情况，向用户汇报"本次领到 N 张券"，并按优惠力度（预计可省金额 × 使用场景）排序展示前几张。

无券可领时如实告知，并建议用户关注 `campaign-calendar` 中的活动日历，活动上新时券会同步更新。

## 工作流 B：省钱点餐（官方渠道精算引擎）

### B1. 确定就餐方式与门店

先向用户确认就餐方式，四选一：到店自取（beType=1）/ 得来速（beType=5）/ 麦乐送到家（beType=2）/ 企业团餐（beType=6）。

- 到店 / 得来速：调用 `query-nearby-stores`（必传 beType、searchType；searchType=1 搜收藏餐厅，searchType=2 按 city + keyword 搜索）。得来速门店返回 beCode，后续调用必须透传。
- 麦乐送 / 团餐：先 `delivery-query-addresses` 查配送地址（无地址时引导 `delivery-create-address` 新建），再 `delivery-query-stores` 查可配送门店，取 beCode。
- 预约取餐场景记录用户期望时间（格式 `yyyy-MM-dd HH:mm`），后续所有工具调用透传 `reservationDate`。

### B2. 获取菜单与门店可用券（并行）

- `query-meals`（storeCode + orderType + beType [+ beCode]）拉取可售餐品与商品编码。
- `query-store-coupons`（同上参数）查询**当前门店 + 订单类型**下可用的优惠券。

⚠️ 判断"这单能用什么券"必须用 `query-store-coupons`；`query-my-coupons` 只反映卡包资产，不承诺当前订单可用。

### B3. 比价（官方渠道内的比价引擎）

用户选定商品后，用 `calculate-price` 做方案矩阵试算：

1. **基线方案**：不带券试算，得到原价应付总价（也是工作流 E 中官方渠道的参照锚点）。
2. **券方案**：对每张门店可用券，将 `couponId` + `couponCode` 挂到对应商品的 items 上试算（一张券只挂一个方案，不叠加）。
3. **汇总对比**：所有方案列成表格——券名称、优惠金额、应付总价；外送场景的"总价"必须包含配送费后再比较。
4. **推荐最优**：选出应付总价最低的方案；若最优券有使用门槛（如满 X 可用），提示用户"再加 Y 元的 Z 商品可改用这张券，到手价更省"，但必须验证凑单后的总价确实低于当前最优，避免为凑单反而多花钱。

展示价格时注意：`calculate-price` 返回金额单位为**分**，需除以 100 转为元。汇报时明确"帮你省了 XX 元"（对比基线方案）。

### B4. 下单

用户确认方案后调用 `create-order`：

- 到店 / 得来速：必传 `takeWayCode`（取值来自 `calculate-price` 返回的 `takeWayList[].code`，先和用户确认取餐方式）。
- 麦乐送 / 团餐：必传 `addressId`；备注（remark，最多 50 字）引导用户填写。
- items 透传 B3 最优方案的 productCode / quantity / couponId / couponCode / modification。
- 创建成功后引导用户支付，支付后可用 `query-order` 跟踪状态；用户反悔时 `cancel-order` 取消。

## 工作流 C：积分变现

1. `query-my-account` 查积分账户：可用积分、累计积分、**即将过期积分**。
2. 存在即将过期积分时主动提醒；调用 `mall-points-products` 查积分商城可兑换商品（catRuleIds 筛选：`1>4` 商品券 / `2` 实物 / `2>8` 周边等）。
3. 按积分性价比推荐兑换项，用户选定后 `mall-product-detail` 看详情，确认后 `mall-create-order` 完成兑换。
4. 兑换记录用 `mall-order-list` / `mall-order-detail` 追踪。

有抽奖活动时可用 `query-lottery-info` 查活动信息，向用户披露消耗规则后由用户决定是否 `draw-lottery`；奖品记录用 `query-my-prizes` 查询。

## 工作流 D：资产盘点

并行调用 `query-my-coupons`（卡包券，支持分页）+ `query-my-account`（积分），输出资产全景：

- 可用券按"即将到期优先"排序，标注有效期，提醒优先使用。
- 积分部分高亮即将过期积分，并给出工作流 C 的兑换建议。
- 结尾主动提示："要不要现在按最划算的方式点一单？"衔接工作流 B（用户提及外部平台价时衔接工作流 E）。

## 省钱策略规则

1. **领券优先**：任何比价/下单动作前先执行工作流 A，麦麦省的券零成本、领了不亏。
2. **比价必做**：至少对比"基线原价 vs 每张可用券"的应付总价，禁止跳过比价直接下单。
3. **总价口径统一**：外送场景比价必须含配送费；到店场景关注取餐方式是否引入额外费用；跨平台比价统一为"到手总价"。
4. **凑单要算总账**：为满足券门槛加购后，只有总价仍低于当前最优方案时才推荐凑单。
5. **积分不闲置**：每次资产盘点发现即将过期积分必须提醒兑换。
6. **外部报价只录不猜**：抖音/美团价格一律由用户提供，绝不虚构或臆测外部价格；无法核实的限制条件标注"以券面规则为准"。
7. **小价差看便利**：渠道间价差小于 2 元时，把官方渠道的便捷性（可直接下单、累积积分、可退款、免核销）纳入推荐考量。

## 注意事项

- 餐品信息、价格及供应状态以麦当劳官方渠道的实时结果为准；本 Skill 输出仅供参考，不构成专业建议。
- 用户 MCP Token 属敏感信息，任何情况下不得在对话、日志或输出中回显。
- 外部平台（抖音/美团）信息不抓取、不臆测，仅基于用户口述录入；比价结论中的外部价格须注明"以平台实际结算价为准"。
- 返回 401 时提示用户检查 Token 配置；返回 429 时说明已限流并降低调用频率。
- 套餐特制（modification）的传参规则较复杂（selectedKey / unselectedKey），详见 `references/tools-guide.md`，未理解规则前不要构造 modification 参数。
